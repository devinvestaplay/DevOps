# Controlled deployments (Milestone 7)

Milestone 7 adds a project and environment scoped server deployment engine. The browser submits a configuration ID and its configured branch, never a shell command, repository URL, server path, or rollback SHA. This milestone does not add arbitrary remote shell access, automatic production deployment, Expo builds, application database migrations, or a multi-party approval system.

## Architecture and configuration

An Admin configures a validated Linux execution account per deployment target. Existing configurations have no account until one is set, and preflight fails closed without it. SSM runs fixed application commands under that account using `runuser`; the command checks the target account's passwd HOME and clears inherited `PM2_HOME`. A configured SSH host alias is accepted only when `ssh -G` resolves it to `github.com`, and the Git remote must still match the linked owner and repository. Do not add Git `safe.directory` exceptions.

An Admin saves a disabled deployment configuration under a project. It binds one active environment, mapped EC2/SSM server, verified GitHub App integration, configured default branch, server repository path, application path inside that repository, exact PM2 process name, and loopback HTTP health URL. Optional npm dependency installation uses `npm ci --ignore-scripts`; optional build uses `npm --ignore-scripts run build`. Both default to off. Review the project's `build` script before enabling the build strategy: npm still executes the named script, so a script that runs a migration must never be enabled for this milestone. The platform stores no GitHub token or AWS credential in the configuration. The GitHub App key remains a server-side secret reference; the mapped AWS integration uses the server's configured SDK identity.

Only the configured GitHub default branch can be requested. The GitHub App resolves its exact 40-character head SHA. The server's Git origin must match that owner and repository through one of the fixed HTTPS or SSH forms. A separate preflight uses SSM for read-only Git revision and clean tracked worktree, Node/package metadata, exact PM2 process, and loopback health probes. It also checks the linked AWS account, EC2 Running state, and SSM Online state. The probe does not fetch, check out, install, build, restart, or modify files. The Git status probe sets `GIT_OPTIONAL_LOCKS=0` to avoid updating Git's index.

The initial status is `awaiting_confirmation`. Confirmation requires the same Admin who ran production preflight to type a challenge containing the project, environment, server, and target SHA within ten minutes. The API rechecks the AWS target, GitHub head, and server revision. If the current SHA equals the target SHA, confirmation is rejected without a restart. A database unique key locks the project/environment/server target from `queued` through execution and any pending rollback.

On confirmation, the API records ordered steps: capture current SHA, fetch the configured branch, detach-checkout the resolved target SHA, optional install, optional build, restart the exact PM2 process, and verify the configured local health endpoint. The step runner is serialized and stops at the first failure. Every SSM command targets the single mapped instance; no user-authored action or script is accepted. The fixed templates validate paths, branch, SHA, process name, and local URL before interpolation. Before invoking PM2, the template requires an existing RPC socket and live daemon PID so a read-only list request cannot initialize a new PM2 daemon. A service managed under a different Unix account will require an explicit PM2-home configuration before this version can safely inspect or restart it. SSM command IDs, step statuses, exit codes, and bounded sanitized output are persisted. The overall status moves through `queued`, `in_progress`, `verifying`, and `succeeded`; an early failure becomes `failed`, while a failure after checkout may have begun becomes `rollback_pending`. The lock remains during uncertain or failed rollback state.

If the post-restart health check fails, the runner starts one automatic rollback to the recorded previous SHA. It first captures the live SHA and refuses to overwrite an unexpected revision, then checks out the previous SHA, runs the configured optional install/build against that revision, restarts only the configured PM2 process, and checks health again. The deployment retains its original failure code and becomes `rolled_back` only after restored-version health succeeds. A rollback failure becomes `rollback_failed`, retains the target lock, and requires immediate manual intervention. The saved `manual` rollback setting applies to other failures after checkout; those remain `rollback_pending` and require an Admin to confirm the prior SHA separately. There is no automatic retry. A process crash or a command that exceeds the polling limit can leave a locked, nonterminal record; investigate the SSM command and server state before any manual recovery. No generic unlock or arbitrary rollback command is exposed. Git rollback does not reverse application database changes, so migrations are excluded from this engine.

Developers can read configurations and history. Release Managers may initiate nonproduction preflights and confirmations. Admins manage configurations and are required for production preflight, confirmation, and rollback. All routes resolve project-scoped IDs server side; the database lock is independent of the UI. The local application remains bound to loopback and is not a hardened public production control plane.

## Real production acceptance runbook

1. Verify the intended project, production environment, AWS mapping, and GitHub App integration from the UI. Confirm the GitHub connection is read-only and connected. Do not enter a private key or token in the browser.
2. Use only read-only observation to verify the real repository root, origin identity, current revision, application path, exact PM2 process, and local health URL. Do not assume historical project paths. Save the reviewed values in a disabled configuration, with install and build set to **None** unless their scripts have been reviewed for migrations and other unintended operations.
3. Enable the configuration, select it on **Deployments**, and run **read-only preflight**. Review the project, environment, instance, repository, branch, current and target SHA, application path, process, health URL, and persisted preflight record. If a value differs, stop and correct the configuration; do not confirm.
4. Stop after a successful real preflight and request separate explicit authorization for exactly one production deployment. A dry run is not authorization to deploy. If current and target SHA match, stop without a restart or synthetic source change.
5. Once separately authorized, verify that the typed challenge and target still match the approved plan, then confirm once through DevOpsPannel. Track its deployment ID, every SSM command ID, step, final health check, and overall status. Do not retry on failure.
6. If execution fails, record the failed step, previous SHA, current server revision and health. A post-restart health failure initiates one automatic rollback; verify its final status and restored-version health. Other failures require a separate rollback decision using only the platform's recorded prior SHA. Do not run application database migrations through this workflow.

## Platform rollback and limits

The DevOpsPannel schema changes are `apps/api/drizzle/0006_loud_marvel_apes.sql`, `0007_secret_hellion.sql`, and `0008_futuristic_rictor.sql`, applied only to the guarded local DevOpsPannel development database. Revert the platform code to the prior commit if necessary; preserve deployment records and do not reverse tables with active records. Application source and database rollback are distinct. The current engine runs in the API process rather than a durable worker, so operator inspection is required after an API crash or ambiguous SSM status. Production use also requires review of the existing dependency advisories in `docs/security-debt.md` and a deployment-specific credential/access policy.
